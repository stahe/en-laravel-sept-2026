    3. The Action Template

    An action requires information sent by the browser: the parameters of the URL ([?nom=martin&age=42]), form fields, the request body JSON, and sometimes a request header HTTP. The original course refers to all of this information as the action model. This chapter shows how an action [Laravel] retrieves this information, converts it to the correct type, and validates it. This process is called data binding.

    [Laravel] provides access to the request information via the [Request] object (Example 05), in the form of character strings, along with a few conversion methods. To verify the data, it has a comprehensive validation system: the expected data is described using rules (“required,” “an integer between 0 and 150,” etc.), and [Laravel] checks that the data complies with them. We’ll first read the parameters manually (example 07), then use these rules to validate them (examples 08 through 12). In the next chapter, the same system will validate the HTML forms.

    Note on terminology: In the next chapter, the word “model” will primarily refer to the data that an action passes to its view. An action’s model, as used in this chapter, is what it receives. [Laravel] also uses the word *model* for the classes that represent database tables (Chapter 9): this is a third meaning.

    Examples 07 through 12 are run in the same way as those in the previous chapter: open a terminal in the example directory, [php artisan serve]; [Ctrl-C] stops the server. Their [bootstrap/app.php] files are all similar: they add the [JsonLisible] middleware from Example 03, resulting in a readable JSON file. We will only comment on them when they introduce something new.

    <?php
// app/Http/Controllers/ParametresController.php: the parameters of URL (the "query string")

namespace App\Http\Controllers;

use Illuminate\Http\Request;

class ParametresController
{
     // /settings/action01?name=martin: the query returns the parameter's value, or
     // null if it is missing
    public function action01(Request $request): string
    {
        $nom = $request->query('nom');
        return "nom = [$nom], de type ".get_debug_type($nom);
    }

     // /parameters/action02?age=42: integer CONVERTIT the value (a string) as
     // integer; a missing parameter, or one that is not an integer, returns 0
    public function action02(Request $request): string
    {
        $age = $request->integer('age');
        return "age = [$age], de type ".get_debug_type($age);
    }

     // /parameters/action03?age=42: a parameter OBLIGATOIRE; if it is missing, or if a
     // value that is not an integer, stops the action with a 400 (Bad Request) response
    public function action03(Request $request): string
    {
        $texte = $request->query('age');
        if ($texte === null) {
             // abort throws an exception, which Laravel converts into an error response
            abort(400, 'le paramètre [age] est obligatoire');
        }
         // we are responsible for the conversion: filter_var returns the integer or false
        $age = filter_var($texte, FILTER_VALIDATE_INT);
        if ($age === false) {
            abort(400, "[$texte] n'est pas un nombre entier");
        }
        return "age = [$age], de type ".get_debug_type($age);
    }

     // /parameters/action04?page=2: a default value if the parameter is missing
    public function action04(Request $request): string
    {
        $page = $request->integer('page', 1);
        return "page = [$page]";
    }

     // /parameters/action05?q=laravel: the name of the parameter in URL is not necessarily
     // the same as that of the variable PHP
    public function action05(Request $request): string
    {
        $recherche = $request->query('q');
        return "recherche = [$recherche]";
    }

     // /settings/action06?name=martin&age=42: all parameters at once, in an array
    public function action06(Request $request): array
    {
        return $request->query();
    }
}
    • line 14: the [query] method in the request returns the value of a parameter from URL, which has already been decoded, or [null] if it is missing; it never causes an error;
    • Line 15: The action displays the value and its type: the [get_debug_type] function returns the name of a value’s type. A value retrieved from URL is always a string ([string]). The operator [.] concatenates the interpolated string and the type;
    • line 22: the method [integer] reads the parameter and converts it to an integer. If the conversion fails ([abc]), or if the parameter is missing, it returns 0: the action cannot distinguish these cases from an age of 0 that was actually entered, and the input error goes unnoticed. Similarly, there are [float], [boolean] ([1], [true], [on], [yes] are valid), [string], [date] (example 12), [enum];
    • lines 30–40: a required parameter and a manual conversion that distinguishes between the two possible errors. [abort(400, message)] terminates the action with a 400 response (*Bad Request*, the request is invalid), accompanied by the message (see example 03). The function [filter_var] of [PHP], with the filter [FILTER_VALIDATE_INT], returns the integer contained in the string, or [false] if the string is not an integer;
    • line 46: the second parameter of [integer] is a default value, used if the parameter is missing. This is typically the case for a page number in a list;
    • line 54: There is no requirement to name the variable [PHP] the same as the parameter of URL. Search engines often use a short parameter, such as [q] (*query*);
    • line 61: without a parameter, [query] returns all the parameters of URL in an associative array, which the action returns: [Laravel] transforms it into JSON (see example 03).

    This first example illustrates the limitations of the manual approach: for each parameter, you must write the reading, conversion, and handling of missing values and errors. With ten parameters, the action’s code would be overwhelmed by these checks. It is better to describe what is expected and let the framework verify it. That is the purpose of the following example.

    3.2. Example 08: An action model described by a class

    [Laravel] validates request data using validation rules. A rule has a name ([required], [integer], [email]...), and sometimes parameters ([min:2], [between:0,150]); the rules for a field are written as a string, separated by [|], or as an array. [Laravel] provides about a hundred of them. The natural place to describe an action’s model is a form request (*form request*): a class that inherits from [FormRequest], and whose [rules] method returns the rules for each parameter.

    <?php
// app/Http/Requests/PersonneRequest.php: the action model, a class that
// describes the expected parameters and their constraints

namespace App\Http\Requests;

use App\Models\Personne;
use Illuminate\Foundation\Http\FormRequest;

class PersonneRequest extends FormRequest
{
     // the validation rules, parameter by parameter
    public function rules(): array
    {
        return [
             // required, a string of 2 to 20 characters
            'nom' => 'required|string|min:2|max:20',
             // required, an integer between 0 and 150
            'age' => 'required|integer|between:0,150',
             // only one of these three values
            'titre' => 'required|in:Mr,Mme,Melle',
             // optional (nullable); if present, a valid email address
            'email' => 'nullable|email',
        ];
    }

     // the validated parameters, in the form of a typed object
    public function personne(): Personne
    {
        $valeurs = $this->validated();
        return new Personne($valeurs['nom'], (int) $valeurs['age'], $valeurs['titre'],
            $valeurs['email'] ?? null);
    }
}
    • Line 10: The class ([extends]) inherits from [FormRequest], which itself inherits from [Request]: A [PersonneRequest] object is a query, with all the methods from Example 07, plus validation rules;
    • lines 13–24: the rules, in an associative array: for each parameter, the string containing its rules;
    • line 17: [required]: the parameter is required (if missing or empty, it is rejected); [string]: a string; [min:2] and [max:20]: for a string, its length must be between 2 and 20 characters;
    • line 19: [integer]: the value must be an integer (["42"] is valid, ["abc"] is not); [between:0,150]: For a number, its value must be between 0 and 150. The rules [min], [max], and [between] thus adapt to the value’s type: a length for a string, a value for a number, and a number of elements for an array (e.g., 10);
    • line 21: [in:Mr,Mme,Melle]: one of the three values listed, and only those;
    • line 23: [nullable]: the parameter is optional (it is accepted if absent or empty); [email]: if present, a valid email address;
    • lines 28–33: a method added to the class: it returns the validated data in the form of a [Personne] object (see below). [$this->validated()] returns only the data that has been validated: a parameter without a rule is not included. The validation performed by [Laravel] checks the data but does not convert it: the validated age is still the string ["42"]. It is the conversion operator [(int)] that converts it to an integer. The operator [??] returns its left operand if it exists and is not [null]; otherwise, it returns the right operand: [$valeurs['email'] ?? null] evaluates to [null] if the address is not in the array.

    This template describes the expected data; it contains no validation instructions. This is known as a declarative style. The class [Personne] is an immutable class, modeled after the one in Example 03:

    <?php
// app/Http/Controllers/PersonnesController.php: an action whose model is a class FormRequest

namespace App\Http\Controllers;

use App\Http\Requests\PersonneRequest;

class PersonnesController
{
     // /people/action01?name=martin&age=42&title=Mr
     // The parameter of type PersonneRequest is VALIDÉ by Laravel AVANT when calling
     // the action: an invalid model raises a ValidationException error, which is converted to
     // a 400 response by bootstrap/app.php, and the action is never called
    public function action01(PersonneRequest $request): array
    {
        $personne = $request->personne();
        return [
            'recu' => $request->validated(),
            'personne' => $personne,
            'typeAge' => get_debug_type($personne->age),
        ];
    }
}
    • Line 14: The action requires a parameter of type [PersonneRequest], whereas Example 07 required a [Request]. [Laravel] then creates a [PersonneRequest] object from the current request and validates it before calling the action: it checks each rule for each parameter. If all rules are met, the action is called. Otherwise, [Laravel] throws a [ValidationException] exception, which contains a list of all errors (not just the first one), and the action is never called: it therefore does not have to deal with invalid data;
    • Lines 16–20: The action returns the validated data as-is, then as a [Personne] object, along with the age type, to illustrate the difference.

    Who handles the [ValidationException] exception? By default, [Laravel] itself, and its response depends on the client. For a request expecting JSON (header [Accept: application/json]), the response is a 422 (*Unprocessable Content*), which describes the errors in JSON. For a regular request originating from a HTML form, the response is a redirect to the previous page, with the errors preserved for the form that will be redisplayed (we’ll cover this in the next chapter). Here, we want an error response in JSON, in all cases, with the 400 code. That is the role of [bootstrap/app.php].

// bootstrap/app.php: the application from Example 08

use App\Http\Middleware\JsonLisible;
use Illuminate\Foundation\Application;
use Illuminate\Foundation\Configuration\Exceptions;
use Illuminate\Foundation\Configuration\Middleware;
use Illuminate\Validation\ValidationException;

(require __DIR__.'/../../vendor/autoload.php')->addPsr4('App\\', __DIR__.'/../app/');

return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(web: __DIR__.'/../routes/web.php')
    ->withMiddleware(function (Middleware $middleware): void {
        $middleware->append(JsonLisible::class);
    })
    ->withExceptions(function (Exceptions $exceptions): void {
         // an invalid template: the exception ValidationException becomes, for
         // TOUTE the application, a 400 response that details the errors
        $exceptions->render(function (ValidationException $e) {
            $erreurs = [];
             // errors(): field -> list of its error messages
            foreach ($e->errors() as $champ => $messages) {
                foreach ($messages as $message) {
                    $erreurs[] = ['champ' => $champ, 'message' => $message];
                }
            }
            return response()->json(['statut' => 400, 'erreurs' => $erreurs], 400);
        });
    })
    ->create();
    • Lines 17–30: The [withExceptions] method is now passed a function, which receives the [$exceptions] object describing the application’s exception handling;
    • lines 20–29: The [render] method registers an exception handler: a function that [Laravel] calls when an action throws an exception of the same type as its parameter (here, [ValidationException] or a derived class), and whose return value is the response sent. [Laravel] identifies the type of the exception being handled based on the function’s parameter type. Declared in [bootstrap/app.php], the handler applies to all actions in the application: every action that validates a model benefits from it, without having to write a single line of error-handling code;
    • Lines 23–27: [$e->errors()] returns errors in an associative array: for each field with an error, the list of its error messages. The [foreach ($tableau as $cle => $valeur)] loop iterates through both the keys and the values. [$erreurs[] = ...] adds an element to the end of the [$erreurs] array;
    • line 28: a response JSON, with status code 400.

use App\Http\Requests\PersonneRequest;

class PostController

     // the fields of a form HTML (body application/x-www-form-urlencoded):
     // post() returns the request parameters from CORPS as an array

    {

            'typeRecu' => $request->header('Content-Type'),

     // a JSON body: json() deserializes it; isJson() checks the declared type
    public function action02(Request $request): array
    {
        if (! $request->isJson()) {
            abort(415, 'le corps de la requête doit être du JSON');
        }
         // json_decode, with JSON_THROW_ON_ERROR: an invalid JSON raises an exception
        try {
            $corps = json_decode($request->getContent(), true, flags: JSON_THROW_ON_ERROR);
        } catch (JsonException $e) {
            abort(400, 'JSON mal formé : '.$e->getMessage());
        }
        return ['typeRecu' => $request->header('Content-Type'), 'corps' => $corps,
            'nom' => $request->input('nom')];
    }

     // a single form field
    public function action03(Request $request): string
    {
        $nom = $request->input('nom');
        return "nom = [$nom]";
    }

     // form fields, validated by the rules of the PersonneRequest class
    public function action04(Request $request): array
    {
        $validateur = Validator::make($request->post(), (new PersonneRequest())->rules());
        $erreurs = [];
        foreach ($validateur->errors()->messages() as $champ => $messages) {
            $erreurs[] = "$champ : $messages[0]";

        sort($erreurs);
        return ['personne' => $erreurs ? null : $validateur->validated(),
            'valide' => ! $erreurs, 'erreurs' => $erreurs];

// app/Liaison/JourFr.php: a French date "23-09-2026" in the path of URL

namespace App\Liaison;

use Carbon\CarbonImmutable;
use Illuminate\Contracts\Routing\UrlRoutable;

// a type that knows how to LIER to a route parameter (resolveRouteBinding) and
// to revert to a segment of URL (getRouteKey): the UrlRoutable interface
class JourFr implements UrlRoutable
{
    public function __construct(public ?CarbonImmutable $date = null)
    {
    }

     // path text -> JourFr object; null: the value is invalid (error 404)
    public function resolveRouteBinding($valeur, $champ = null): ?static
    {
         // the "!" in "!d-m-Y" sets the time to zero (otherwise, it would be the current time)
        $date = CarbonImmutable::createFromFormat('!d-m-Y', $valeur);
         // createFromFormat accepts "31-02-2026" (and actually converts it to March 3): we verify
         // that the formatted date correctly reflects the received text
        if ($date === null || $date->format('d-m-Y') !== $valeur) {
            return null;
        }
        return new static($date);
    }

     // subject JourFr -> path text (used by the route function)
    public function getRouteKey(): string
    {
        return $this->date->format('d-m-Y');
    }

    public function getRouteKeyName(): string
    {
        return 'jour';
    }

    public function resolveChildRouteBinding($typeEnfant, $valeur, $champ): ?static
    {
        return null;
    }
}
    • line 11: the class implements the [UrlRoutable] interface, whose four methods are as follows;
    • line 13: the date, a [CarbonImmutable] object. [Carbon] is the date library for [Laravel]; It extends the [DateTime] class from [PHP] with hundreds of methods. The [Immutable] version creates a new object with each modification ([$date->addDay()] returns a new date), rather than modifying the existing object. // app/Liaison/DetecterLangue.php: a middleware component that CALCULE provides information for the action

namespace App\Liaison;

use Closure;
use Illuminate\Http\Request;
use Symfony\Component\HttpFoundation\Response;

class DetecterLangue
{
    public function handle(Request $request, Closure $next): Response
    {
         // the "Accept-Language: fr-FR,fr;q=0.9,en;q=0.8" header -> "fr": the browser's
         // the browser’s preferred language from among those offered (the first one by default)
        $langue = $request->getPreferredLanguage(['fr', 'en']);
         // the ATTRIBUTS fields in the request: information that the application stores there
         // for the functions that will process the request afterward
        $request->attributes->set('langue', $langue);
        return $next($request);
    }
}
    • Line 16: The request header [Accept-Language] specifies the user’s languages, in order of preference: [fr-FR,fr;q=0.9,en;q=0.8] (the coefficient [q] measures the preference, on a scale from 0 to 1). [getPreferredLanguage] selects, from among the languages offered by the application, the one the user prefers; if no header is provided, it is the first one on the list;
    • line 19: the request has attributes—an array of information that the application stores there for the functions that will process the request afterward. The language is stored there under the name [langue];
    • Line 20: The request continues on to the action.

    The action will receive this information via an attribute named [PHP] placed before its parameter (see the controller).

    3.6.6. Conclusion

    Let’s summarize the methods available to an action for obtaining its template:

    Route parameters
    the action’s parameters, which share the same name; converted by their type ([int $id]), constrained by [whereNumber], [where]...; bound to an object by [UrlRoutable]
    Parameters of URL
    [$request->query(...)], [integer], [array], [date]...; a repeated parameter is written as [nom[]]
    Fields in a POST form
    [$request->post(...)], or [$request->input(...)], which searches everywhere
    Body JSON
    [$request->input(...)], [$request->json()], or [json_decode($request->getContent())]
    Headers
    [$request->header(...)], and methods that parse them, such as [getPreferredLanguage]
    Validation
    of rules: a [FormRequest] (validation before the action) or [Validator::make] (validation by the action); "custom" rules ([ValidationRule])
    Messages
    the files [lang/xx/validation.php] and the language file [APP_LOCALE]
    Common errors
    [$exceptions->render(...)] in [bootstrap/app.php] (entire application), [failedValidation] (a form request)
    Calculated parameter
    A middleware component that stores information in the request attributes, [#[RequestAttribute]]

    The HTML forms, on the other hand, require more than just validation: they must be displayed, re-displayed with the user’s input and any errors, and protected against forged requests. This is the subject of the next chapter, once views have been introduced.
