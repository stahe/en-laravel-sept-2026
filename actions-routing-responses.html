    2. Actions, Routing, Responses

    This chapter examines the path a request takes, from the browser to the action that processes it, and the response that action returns. Views will not be covered until Chapter 4: here, actions return text or JSON directly.

    • line 2: a comment, from [//] to the end of the line ([/* ... */] delimits a multi-line comment);
    • line 4: the statement [use] imports a class name. The full name of a class [PHP] includes its namespace (*namespace*), the equivalent of packages in [Java]: [Illuminate\Http\Request] is the class [Request] in the namespace [Illuminate\Http]. After [use], the file can simply be named [Request]. [Illuminate] is the code name for the components of [Laravel];
    • Line 7: [require] executes another file, [PHP]. [__DIR__] is the directory of the current file (here, [public]); the operator [.] concatenates two strings. The file [vendor/autoload.php], written by [Composer], installs the class loader: the first time a class is used, it finds and loads the file that defines it. Thanks to this, we never have to write a [require] file for classes. The [vendor] folder is the same as the [exemples] folder, shared by all the examples (see introduction): hence the two [..] files;
    • Line 10: A file executed by [require] can return a value using the instruction [return]: [bootstrap/app.php] returns the application—an object of class [Illuminate\Foundation\Application]—stored in the variable [$app]. In [PHP], variable names always begin with [$]. [require_once] would do nothing if the file had already been executed;
    • line 11: [Request::capture()] calls the static method [capture] of the class [Request] (the operator [::] refers to a member of a class, while the operator [->] refers to a member of an object). It creates a [Request] object from the HTTP request received by [PHP]. [$app->handleRequest(...)] has the application process this request and sends the response to the browser.

    This file is the same for all examples, and—with the exception of two [..] files—is the same as that of a standard [Laravel] project. It highlights a unique feature of [PHP], which explains a lot about [Laravel]: the application is rebuilt with every request. The web server executes [public/index.php] from start to finish for each request it receives: it loads the classes, builds the application, processes the request, sends the response, and then forgets everything. No objects survive from one request to the next. In the chapter on data scopes, we will see the consequences of this behavior, which is the opposite of that of [Java], [C#], or [Python], whose applications remain in memory between requests.

We’ll encounter them throughout the chapters;

    2.1.6. Execution

    In a terminal window open to the [01-structure] folder, type [php artisan serve]. [Laravel] displays:

    1
2

       INFO  Server running on [http://127.0.0.1:8000].

    The command [serve] launches the development server integrated into [PHP] ([php -S]), which is configured to forward all requests to [public/index.php] (except for requests for files located in the [public] folder, which it sends as-is). It listens on port 8000 at the address [127.0.0.1], which is the address of the machine itself ([localhost]): it accepts only requests from this machine, which is suitable for development ([--host=0.0.0.0] would open it to other machines on the network; [--port=8001] would change the port). It is stopped by [Ctrl-C]. This server is intended for development: in production, it will be a web server such as [Apache] or [Nginx], paired with [PHP-FPM] (see case study). It is not necessary to restart it after a code change: since [PHP] re-reads the files with every request, the change takes effect on the next request. Only a change to the file [.env] requires a restart, which the command [serve] performs automatically.

use App\Http\Controllers\AccueilController;

use Illuminate\Support\Facades\Route;

// GET / : the action [index] of the class AccueilController
Route::get('/', [AccueilController::class, 'index']);

// a GROUPE route: the /first prefix and the controller are common to all
Route::prefix('premier')->controller(PremierController::class)->group(function () {
     // GET /first: the group’s ‘/’ route refers to the prefix itself
    Route::get('/', 'index');
     // GET /first/action01
    Route::get('action01', 'action01');
     // POST /first/action01: same path, different method HTTP, different action
    Route::post('action01', 'action01Post');
     // GET /first/products/17: {id} is a route parameter; whereNumber
     // accepts only numbers
    Route::get('produits/{id}', 'produit')->whereNumber('id');
     // GET /first/products/17/reviews/3: two route parameters
    Route::get('produits/{id}/avis/{numero}', 'avis')->whereNumber(['id', 'numero']);
     // GET /first/files/... : the expression .* accepts any ending
     // for the path, including slashes
    Route::get('fichiers/{chemin}', 'fichier')->where('chemin', '.*');
});

    • Line 9: The action is no longer an anonymous function, but an array with two elements: the controller class and the method name. [AccueilController::class] is the full name of the class, as a string (['App\Http\Controllers\AccueilController']). For each request [GET /], [Laravel] creates a [AccueilController] object and calls its method [index];
    • line 12: a route group: the routes declared in the function passed to [group] share the group’s settings. [prefix('premier')] prepends [/premier] to their paths; [controller(PremierController::class)] assigns them their controller, and each route then simply needs to name its method. The URL for an action is the concatenation of the group prefix and the path of its route;
    • line 14: the route ['/'] refers to the prefix itself: [GET /premier];
    • Lines 16–18: The same path, HTTP, corresponds to two methods: [GET] and [POST], which are handled by two different actions. There is also [Route::match(['get', 'post'], ...)], for an action that handles multiple methods, and [Route::any], for all of them;
    • Line 21: [{id}] is a route parameter: this segment of URL can take multiple values. By default, a parameter accepts any text without a slash; [whereNumber('id')] restricts the parameter to contain only digits: otherwise, the route does not match. This is a singleton. To switch to an implementation that reads from a database, you would simply need to change this line: the controllers, which only know the contract, would remain unchanged. That is the whole point of dependency injection: every part of the application depends on contracts, and a single location decides on the implementations.

    A concrete class (which is not an interface) does not even need to be declared: the container knows how to create it on its own, by injecting the parameters into its constructor. This is how it creates controllers. An interface, on the other hand, must be associated with an implementation; otherwise, the container fails (“Target [App\Produits\ProduitsService] is not instantiable”). This association can also be declared on the interface itself, using an attribute (an annotation, in [PHP]): [#[Bind(ProduitsServiceMemoire::class)]] above [interface ProduitsService], and [#[Singleton]] above the implementation class. We will keep the declaration in [bootstrap/app.php], which brings together all the application’s choices in a single location; the case study will group them into a service provider, the class that [Laravel] provides for this purpose.

    Finally, a word about the lifetime of this singleton. As we saw in Example 01: in [PHP], the application is rebuilt with each request. The singleton is therefore unique to a single request: all classes that request it during the processing of a request receive the same object, but the next request will receive a new one. For a service that only reads static data, like this one, this makes no difference. For a service whose data changes (the task list in Example 20), this data must be stored somewhere other than in the object: in a file, a database, or the cache of [Laravel]. On the other hand, a [PHP] service cannot be used by two requests at the same time: each request has its own. The precautions required for services shared by multiple simultaneous requests in [Java], [C#], or [Python] (locks, in particular) are unnecessary here.
