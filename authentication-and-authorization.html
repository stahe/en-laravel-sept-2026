    8. Authentication and Authorization

    Two distinct questions arise for each request:

    • Who is the user? This is authentication: the user has identified themselves with a username and password, and every subsequent request must prove that it comes from them;
    • Do they have permission to access this page? This is authorization: in the case study, only a user with the role ADMIN manages doctors and clients.

    Proof of identity must accompany every request. [Laravel] typically stores the logged-in user’s ID in their session (see the chapter on scopes), which is the simplest solution for a web application. The case study, in all its versions ([ASP.NET Core MVC], [Spring MVC], [NestJS], [Flask]), instead uses a token (JWT (*JSON Web Token*)), which we will use here: after login, the server generates a token containing the user’s identity and signs it with a secret key. The token is stored in a cookie; the browser sends it back with every request; the server verifies the signature. The user can read their token but cannot modify it: any modification invalidates the signature. The format is standardized (RFC 7519), understood by all programming languages, and the token includes its expiration date. Most importantly, the server doesn’t need to store anything: any server that knows the key can verify the token.

    [Laravel] has a complete authentication system, the components of which we will use as-is:

    • authentication is handled by a *guard*: an object that, for each request, identifies the authenticated user. [Laravel] provides a guard that reads the session; we’ll write our own, which reads the token, in just a few lines. The rest of the application sees only the guard: [auth()->user()], [#[CurrentUser]], and [@auth] in the views;
    • page protection is handled by route middleware (previous chapter): [auth] requires an authenticated user, [can:admin] requires authorization;
    • authorizations are described by Gates (e.g., 26);
    • Passwords are hashed by the [Hash] facade (using the *bcrypt* algorithm), and attempt limits are enforced by the [RateLimiter] facade (Example 27).

    Token generation and verification are handled by the [firebase/php-jwt] library, the most widely used in [PHP], installed by the [composer.json] file from the examples.

    8.1.1. Configuration: .env, config/jwt.php, and config/auth.php

    The token is signed with a secret key, which must not be hard-coded. It’s time to truly separate the configuration from the code. The settings specific to an installation are in the file [.env] (Example 01), which now includes two new lines:

    <?php
// app/Auth/UtilisateursService.php: users, in memory (Example 28 and
// the case study will store them in a database)

namespace App\Auth;

class UtilisateursService
{
     // we do not store JAMAIS a password, only its bcrypt hash, calculated
     // once and for all using: php -r "echo password_hash('marie', PASSWORD_BCRYPT);"
    private const UTILISATEURS = [
        'marie' => ['Marie Pélissier', 'USER', '$2y$10$2DnOgGBiVcyc07su9rj2E.EvOoyPFzHN/h9PLKDuoW5P7UGtclW6W'],
        'admin' => ['Administrateur', 'ADMIN', '$2y$10$m5o9euCi0EdgoZkLVw.UsO58RxJcqhMBfVrlLMCIOh2LyGSjuN29K'],
    ];

    public function chercher(string $login): ?Utilisateur
    {
        if (! isset(self::UTILISATEURS[$login])) {
            return null;
        }
        [$nom, $role, $hachage] = self::UTILISATEURS[$login];
        return new Utilisateur($login, $nom, $role, $hachage);
    }
}
    • Lines 11–14: Two test users, hard-coded into the program (Example 28 and the case study will populate a database with them): for each login, the name, role, and password hash. The hash is generated using the bcrypt algorithm, which is designed for passwords. It has two distinctive features. It is intentionally slow, with an adjustable level of slowness (the cost, here set to 10: 2^10 computational cycles, resulting in the hash [$10$]): a few tens of milliseconds, imperceptible to a user, but which make it very costly for a hacker to try billions of passwords. It is salted: a randomly generated salt is mixed with the password before hashing and stored within the hash itself (the 22 characters following [$10$]); thus, two users with the same password will have different hashes. The hashes were calculated once and for all by the function [password_hash] from [PHP] (line 10): calculating them with every request would be an unnecessary waste of time, since the application is rebuilt with every request. [bcrypt] considers only the first 72 bytes of a password: the case study takes this into account;
    • Lines 16–23: the user of a login, or [null]. [isset] checks for the existence of a key; the assignment [[$nom, $role, $hachage] = ...] deallocates an array: each variable receives the corresponding element.

    <?php
//app/Auth/AuthService.php: password verification and tokens

namespace App\Auth;

use Firebase\JWT\JWT;
use Firebase\JWT\Key;
use Illuminate\Support\Facades\Hash;
use Throwable;

class AuthService
{
    public function __construct(private UtilisateursService $utilisateurs)
    {
    }

     // the user, or null if the login is unknown or the password is incorrect.
     // Hash::check hashes the entered password with the stored hash salt,
     // then compares the two results
    public function valider(?string $login, ?string $motDePasse): ?Utilisateur
    {
        if (! $login || $motDePasse === null) {
            return null;
        }
        $utilisateur = $this->utilisateurs->chercher($login);
        if ($utilisateur === null || ! Hash::check($motDePasse, $utilisateur->hachageMotDePasse)) {
            return null;
        }
        return $utilisateur;
    }

     // the user’s token (JWT), signed with the secret key (HMAC-SHA256)
    public function creerJeton(Utilisateur $utilisateur): string
    {
        $maintenant = time();
         // the token’s content: the “claims” (statements about the user)
        $claims = [
            'sub' => $utilisateur->login,
            'nom' => $utilisateur->nom,
            'role' => $utilisateur->role,
            'iat' => $maintenant,
            'exp' => $maintenant + config('jwt.duree') * 60,
        ];
        return JWT::encode($claims, config('jwt.secret'), 'HS256');
    }

     // the user described by a token whose signature and expiration date
     // are valid; null otherwise (token is forged, expired, or unreadable)
    public function verifier(string $jeton): ?Utilisateur
    {
        try {
             // decode returns an object; (array) converts it to an associative array
            $claims = (array) JWT::decode($jeton, new Key(config('jwt.secret'), 'HS256'));
        } catch (Throwable) {
            return null;
        }
        return new Utilisateur($claims['sub'], $claims['nom'], $claims['role'], claims: $claims);
    }
}
    • lines 20–30: verification of a username and password. [Hash::check] hashes the entered password using the stored hash salt and compares the two hashes. An unknown username and an incorrect password yield the same result, [null];
    • lines 33–45: generating the token. Its content is an array of claims about the user. Some have standardized names: [sub] (*subject*), the user’s identifier; [iat] (*issued at*), the creation date; [exp] (*expiration*), the expiration date. Dates are expressed in seconds elapsed since January 1, 1970 (the function [time()] of [PHP]). The other fields are optional: here, the name and role. [JWT::encode] generates the token and signs it using the [HS256] algorithm (HMAC-SHA256, a signature using a shared secret key);
    • Lines 49–58: token verification. [JWT::decode] verifies the signature and expiration date, then returns the assertions (an object, converted to an array by [(array)]). Any anomaly (forged, expired, or malformed token) raises an exception; [catch (Throwable)] catches them all ([Throwable] is the interface for all exceptions and errors from [PHP]; the variable name is optional when not used). The [Key] object associates the key with an algorithm: a token that specifies a different algorithm (or none at all, [none]) would be rejected. The valid token becomes a [Utilisateur], without a hash, along with its assertions (parameter named [claims]).

// bootstrap/app.php: the application from Example 25

use App\Auth\AuthService;
use Illuminate\Foundation\Application;
use Illuminate\Foundation\Configuration\Middleware;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Auth;
use Illuminate\Support\Facades\Cookie;

(require __DIR__.'/../../vendor/autoload.php')->addPsr4('App\\', __DIR__.'/../app/');

return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__.'/../routes/web.php',
         // the route used by Bootstrap (see Example 15)
        then: fn () => require __DIR__.'/../../commun/bootstrap.php')
    ->withMiddleware(function (Middleware $middleware): void {
         // The token is already signed: the cookie carrying it is not encrypted
        $middleware->encryptCookies(except: ['jeton']);
         // An anonymous visitor requesting a protected page: redirected to /login
        $middleware->redirectGuestsTo('/login');
    })
    ->withExceptions()
    ->booted(function () {
         // the on-call handler [jwt] (see config/auth.php): a function that receives the
         // request, and returns the authenticated user, or null for an anonymous visitor
        Auth::viaRequest('jwt', function (Request $request) {
            $jeton = $request->cookie(config('jwt.cookie'));
            if ($jeton === null) {
                return null;
            }
            $utilisateur = app(AuthService::class)->verifier($jeton);
            if ($utilisateur === null) {
                 // a cookie that exists but is invalid (expired or forged token): it is deleted
                Cookie::queue(Cookie::forget(config('jwt.cookie')));
            }
            return $utilisateur;
        });
    })
    ->create();
    • line 20: the token is already signed; the cookie carrying it is not encrypted (example 22), which allows it to be examined;
    • line 22: the [auth] middleware will redirect anonymous visitors to the login page;
    • lines 28–39: [Auth::viaRequest] defines a guard driver using a simple function: it receives the request and returns the authenticated user, or [null] for an anonymous visitor. It is called only if the application needs the user, and, once it has found one, [Laravel] retains it for the entire request (for an anonymous visitor, it is called with every request) (the middleware [auth], [auth()->user()]...). It does not reject anything: it determines who the user is. This is authentication. [app(AuthService::class)] requests an object from the container (see Example 06): the function [app] grants access to the container everywhere;
    • Lines 34–39: If the browser sent a cookie but its token is invalid (expired or tampered with), we take this opportunity to delete it. [Cookie::forget] creates an empty cookie that has already expired; [Cookie::queue] queues it: the [AddQueuedCookiesToResponse] middleware in the [web] group will add it to the response, whatever that response may be.

    <?php
// app/Http/Controllers/AuthController.php: login and logout

namespace App\Http\Controllers;

use App\Auth\AuthService;
use Illuminate\Http\RedirectResponse;
use Illuminate\Http\Request;
use Illuminate\View\View;

class AuthController
{
    public function __construct(private AuthService $auth)
    {
    }

    public function accueil(): RedirectResponse
    {
        return redirect('/profil');
    }

    public function formulaire(): View
    {
        return view('auth.login');
    }

    public function connexion(Request $request): View|RedirectResponse
    {
        $login = $request->input('login');
        $utilisateur = $this->auth->valider($login, $request->input('motDePasse'));
        if ($utilisateur === null) {
             // a deliberately vague message: it does not specify whether it is the username or the password
            return view('auth.login', ['login' => $login,
                'erreur' => 'Login ou mot de passe incorrect.']);
        }
         // the token, in a cookie: the page’s JavaScript cannot read it
         // (httpOnly); it does not accompany POST requests coming from other sites
         // (sameSite); it disappears when the token expires (duration in minutes)
        return redirect('/profil')->withCookie(cookie(config('jwt.cookie'),
            $this->auth->creerJeton($utilisateur), config('jwt.duree'),
            httpOnly: true, sameSite: 'lax'));
    }

     // logout: POST only (a simple link placed on another site does not
     //(cannot log the user out without their knowledge); the cookie is deleted
    public function deconnexion(): RedirectResponse
    {
        return redirect('/login')->withoutCookie(config('jwt.cookie'));
    }
}
    • lines 30–34: the login. If the login fails, the form is redisplayed with the entered username and a deliberately vague message: saying “unknown username” would reveal to a hacker which usernames exist;
    • lines 39–41: if successful, the token is stored in a cookie, and the user is redirected to the protected page (schema PRG). The cookie is [httpOnly]: the page’s [JavaScript] cannot read it, which protects the token against script injection (XSS); it is [sameSite: 'lax']: the browser does not send it with a POST request originating from another site, which protects the application against CSRF attacks (example 18); its lifetime (in minutes) is the same as the token’s. In production, for HTTPS, we would add [secure: true]: the cookie would never be sent over an unencrypted connection;
    • Lines 46–49: Logging out deletes the cookie ([withoutCookie]). This is a POST action: a simple link to [/logout], placed on another site or within an image, cannot log the user out without their knowledge. Note a limitation of tokens: the token itself remains valid until it expires. Someone who has made a copy of it could still use it. That is why their lifetime is limited.

    8.3. Example 27: CAPTCHA and Attempt Limits

    A login form is a target: a program can try thousands of passwords per minute (brute-force attack). Two protections complement each other:

    • a CAPTCHA (*Completely Automated Public Turing test to tell Computers and Humans Apart*): an image containing a distorted code that is easy for a human to read but difficult for a program;
    • an attempt limit: after three failed attempts, the client’s address IP is blocked for one minute.

        $h = self::HAUTEUR;

             '<rect width="100%" height="100%" fill="#f5f7fa"/>'];

         // slightly shifted at random

            $angle = self::hasard(-0.35, 0.35);   // rotation, in radians (approximately ±20°)
            $cx = 10 + $pas * ($i + 0.5) + self::hasard(-3, 3);    // center of the character
            $cy = $h / 2 + self::hasard(-4, 4);
            foreach (self::POLICE[$caractere] as $trait) {
                $d = [];
                for ($k = 0; $k < count($trait); $k += 2) {
                     // grid point, centered at (2, 3), distorted, rotated, positioned
                    $x = ($trait[$k] - 2 + self::hasard(-0.2, 0.2)) * $echelle;
                    $y = ($trait[$k + 1] - 3 + self::hasard(-0.2, 0.2)) * $echelle;

                    $py = $cy + $x * sin($angle) + $y * cos($angle);
                    $d[] = sprintf('%s%.1f %.1f', $k === 0 ? 'M' : 'L', $px, $py);
                }

                    implode(' ', $d), self::couleur(), self::hasard(2.2, 3));
            }

                self::hasard(0, 20), self::hasard(5, 45), self::hasard(30, 60), self::hasard(0, 50),
                self::hasard(90, 120), self::hasard(0, 50), self::hasard(130, 150), self::hasard(5, 45),

        }

        return implode('', $morceaux);

// app/Auth/CaptchaService.php: pending CAPTCHAs, stored by the server,
// in the cache (see example 20)

namespace App\Auth;

use Illuminate\Support\Facades\Cache;
use Illuminate\Support\Str;

class CaptchaService
{
     // the lifespan of a CAPTCHA, in seconds
    private const DUREE_VIE = 600;

    public function generer(): Captcha
    {
        $texte = DessinCaptcha::texteAleatoire(5);
         //: a random identifier that is impossible to guess
        $id = Str::random(24);
         // the expected answer, stored in the cache for 10 minutes: the cache will forget it
         // on its own afterward
        Cache::put("captcha:$id", $texte, self::DUREE_VIE);
        return new Captcha($id, DessinCaptcha::svg($texte));
    }

     // the CAPTCHA is CONSOMMÉ in all cases: an image is used only once
    public function verifier(?string $id, ?string $saisie): bool
    {
         // pull: reads the value ET and removes it from the cache (returns null if it doesn’t exist or has expired)
        $attendu = $id ? Cache::pull("captcha:$id") : null;
        if ($attendu === null || $saisie === null) {
            return false;
        }
        return strcasecmp($attendu, trim($saisie)) === 0;
    }

// app/Http/Controllers/AuthController.php: login (with CAPTCHA and attempt limit) and logout

namespace App\Http\Controllers;

use App\Auth\AuthService;
use App\Auth\CaptchaService;
use Illuminate\Http\RedirectResponse;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\RateLimiter;
use Illuminate\View\View;

class AuthController
{
     // Maximum of 3 failed attempts within 60 seconds
    private const MAX_ECHECS = 3;

    private const DUREE_BLOCAGE = 60;

    public function __construct(private AuthService $auth, private CaptchaService $captchas)
    {
    }

    public function accueil(): RedirectResponse
    {
        return redirect('/profil');
    }

    public function formulaire(): View
    {
        return $this->pageLogin();
    }

    public function connexion(Request $request): View|RedirectResponse
    {
        $login = $request->input('login');
         // The key for the failure counter: the client's address IP
        $cle = 'login:'.$request->ip();

         // 1. A blocked address isn’t even listened to
        if (RateLimiter::tooManyAttempts($cle, self::MAX_ECHECS)) {
            $secondes = RateLimiter::availableIn($cle);
            return $this->pageLogin($login, "Trop de tentatives : réessayez dans $secondes s.");
        }
         // 2. Captcha first (low-cost), password (bcrypt, high-cost) next
        if (! $this->captchas->verifier($request->input('captchaId'), $request->input('captcha'))) {
            RateLimiter::hit($cle, self::DUREE_BLOCAGE);
            return $this->pageLogin($login, "Le code de l'image est incorrect.");
        }
        $utilisateur = $this->auth->valider($login, $request->input('motDePasse'));
        if ($utilisateur === null) {
            RateLimiter::hit($cle, self::DUREE_BLOCAGE);
            return $this->pageLogin($login, 'Login ou mot de passe incorrect.');
        }
        RateLimiter::clear($cle);
        return redirect('/profil')->withCookie(cookie(config('jwt.cookie'),
            $this->auth->creerJeton($utilisateur), config('jwt.duree'),
            httpOnly: true, sameSite: 'lax'));
    }

    public function deconnexion(): RedirectResponse
    {
        return redirect('/login')->withoutCookie(config('jwt.cookie'));
    }

     // Each time the form is displayed, it generates a NOUVEAU CAPTCHA
    private function pageLogin(?string $login = null, ?string $erreur = null): View
    {
        return view('auth.login', ['login' => $login, 'erreur' => $erreur,
            'captcha' => $this->captchas->generer()]);
    }
}
    • line 38: The limit is handled by the [RateLimiter] facade of [Laravel], which counts “attempts” under a key in the cache. The key here is the client’s address IP;
    • lines 41–44: A blocked address is not even listened to. [tooManyAttempts(clé, 3)] is true if the key has reached 3 attempts; [availableIn] returns the number of seconds remaining before the block ends;
    • lines 46–54: The CAPTCHA is verified before the password; verifying it costs almost nothing, whereas [bcrypt] is intentionally slow. A program that enters the wrong CAPTCHA would therefore not trigger [bcrypt]. Each failure—whether for the CAPTCHA or the password—is counted: [RateLimiter::hit(clé, 60)] adds one attempt and sets the counter’s lifetime to 60 seconds. On the third failure, the address is therefore blocked until the end of those 60 seconds, counted from the first failure;
    • line 55: a successful login clears the failed attempts;
    • lines 67–71: Each time the form is displayed, a new CAPTCHA is generated, even after a failed attempt.

    [Laravel] also provides a middleware component, [throttle], which limits the number of requests for a route ([->middleware('throttle:5,1')]: 5 requests per minute); we chose to count only the failed attempts, so as not to inconvenience a user who is logging in normally.
