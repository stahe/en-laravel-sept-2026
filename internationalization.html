    5. Internationalization

    An internationalized application displays its text in the user’s language. The case study is in French and English. The principle is simple: the views no longer contain text, but keys ([MENU.ACCUEIL]), and a dictionary for each language associates a text with each key. The selected language is stored in a cookie.

    [Laravel] has its own translation system, which we already encountered in Example 09 for validation messages. It accepts two types of dictionaries, stored in the [lang] folder: [PHP] files, one per theme and per language ([lang/fr/validation.php]), which return an array of keys; and JSON files, one per language ([lang/fr.json]), where each key is an arbitrary string. We use the second format: apart from the parameter syntax, these are the same dictionaries as those in versions [ASP.NET Core MVC], [NestJS], [Spring MVC], and [Flask] from the case study, and their format can be read and written without any special tools. The formatting of dates and amounts remains the same as in Example 16.

    A JSON dictionary is an object in which each pair associates a key with its text. Keys are grouped by theme based on their prefix: the menu text “Home” has the key [MENU.ACCUEIL]. A text may contain placeholders, written as [:nom], which are replaced during translation. (The dictionaries in the other versions of the case study nest the objects JSON — [{"MENU": {"ACCUEIL": "Accueil"}}] — and write the parameters as [{nom}]; those in [Laravel] are “flat” and use the [:nom] syntax.)     If a key is missing from the JSON dictionary for the current language, it is searched for in the [PHP] files in that language’s folder ([lang/fr/*.php], example 09), and then in those for the fallback language ([APP_FALLBACK_LOCALE], English by default). There is no backup dictionary (JSON): a key missing from the current language’s dictionary (JSON) and from these files is displayed as-is. This way, any omission is immediately visible on the screen.

    <?php
// app/Http/Middleware/DefinirLangue.php: the language of each request

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\App;
use Symfony\Component\HttpFoundation\Response;

class DefinirLangue
{
     // the supported languages; the first is the default language
    public const LANGUES = ['fr', 'en'];

    public const COOKIE = 'langue';

     // the language of the [langue] cookie, if supported; otherwise, French
    public function handle(Request $request, Closure $next): Response
    {
        $langue = $request->cookie(self::COOKIE);
        App::setLocale(in_array($langue, self::LANGUES, true) ? $langue : self::LANGUES[0]);
        return $next($request);
    }
}
    • lines 14–16: the supported languages and the cookie name: public class constants, accessible from other classes ([DefinirLangue::LANGUES]);
    • lines 21–22: Before each action, the request language: the language specified in the [langue] cookie if one exists and is supported; otherwise, French. [$request->cookie(nom)] returns the value of a cookie sent by the browser, or [null]. [in_array], with [true] as the third parameter, also compares the types ([===]). [App::setLocale] (example 16) sets the application language for the request: this is the language used for translations and formatting.

    ->withMiddleware(function (Middleware $middleware): void {
         // the cookie [langue] is not encrypted: it contains nothing confidential, and
         // the server only accepts supported languages
        $middleware->encryptCookies(except: [DefinirLangue::COOKIE]);
         // the language of each request: the one in the [langue] cookie, or French otherwise
        $middleware->web(append: DefinirLangue::class);
    })
    ->withExceptions()
    ->booted(function () {
         // in views: @currency($prix) (see Example 16)
        Blade::directive('monnaie', fn (string $expression) =>
            "<?php echo e(\\App\\Aides\\Formats::monnaie($expression)); ?>");
    })
    ->create();
    • Line 19: By default, [Laravel] encrypts all cookies it sets and decrypts those it receives (this is the role of the [EncryptCookies] middleware in the [web] group; see Example 20): The user cannot read or create an encrypted cookie. The [langue] cookie contains no secret information, and the server accepts only supported languages: we exclude it from encryption, which allows us to view (and create) it using [curl]. The following example will revisit this encryption;
    • line 21: the language middleware, at the end of the [web] group (Example 16): it runs after [EncryptCookies] and therefore reads cookies that have already been decrypted;

    <?php
// app/Help/Formats.php: dates and amounts, formatted in the request language (see Example 16)

namespace App\Aides;

use Brick\Math\BigDecimal;
use Carbon\CarbonInterface;
use Illuminate\Support\Facades\App;
use Illuminate\Support\Number;

class Formats
{
     // an amount in euros
    public static function monnaie(BigDecimal $montant): string
    {
        return Number::currency($montant->toFloat(), in: 'EUR', locale: App::getLocale());
    }

     // a date written out in full. The "dddd LL" format: the day of the week, followed by the
     // date in the language’s “long” format: “mercredi 23 septembre 2026” in French,
     // "Wednesday, September 23, 2026" in English
    public static function dateLongue(CarbonInterface $jour): string
    {
        return $jour->locale(App::getLocale())->isoFormat('dddd LL');
    }
}
    • Line 24: [LL] is a localized format: each language has its own ([23 septembre 2026] in French, [September 23, 2026] in English), whereas [D MMMM YYYY] would impose the French order on all languages. [dddd] adds the day of the week.

    <?php
// app/Http/Controllers/LangueController.php: the language selection

namespace App\Http\Controllers;

use App\Http\Middleware\DefinirLangue;
use Illuminate\Http\RedirectResponse;
use Illuminate\Http\Request;

class LangueController
{
     // GET /language/en: stores the selection in a cookie, then returns to the previous page
    public function changer(Request $request, string $code): RedirectResponse
    {
        abort_unless(in_array($code, DefinirLangue::LANGUES, true), 404);
         // the cookie: one year lifetime (in minutes), unreadable by the JavaScript of the
         // page (httpOnly), never sent with a POST request originating from another site (sameSite)
        return redirect(self::pageDOrigine($request))
            ->withCookie(cookie(DefinirLangue::COOKIE, $code, 365 * 24 * 60, httpOnly: true, sameSite: 'lax'));
    }

     // the page from which the request originated (Referer header), of which only the path is retained:
     // redirecting to a full URL from the request would allow
     // to send the user to another site (“open redirect” vulnerability)
    private static function pageDOrigine(Request $request): string
    {
         // parse_url breaks down a URL into its components (path, parameters, etc.)
        $url = parse_url($request->header('Referer', ''));
        $chemin = $url['path'] ?? '';
         // "//site.com/..." would be interpreted by the browser as a URL
         // on a AUTRE site: also rejected
        if (! str_starts_with($chemin, '/') || str_starts_with($chemin, '//')) {
            return '/';
        }
        return isset($url['query']) ? "$chemin?{$url['query']}" : $chemin;
    }
}
    • line 15: an unknown language code: 404;
    • lines 18–19: the action responds with a redirect to the page the user came from; the user is taken back to that page in the new language. The response includes a cookie, which the browser will send back with every request: the function [cookie] creates it, and the method [withCookie] adds it to the response. Its parameters: the name, the value, the lifetime in minutes (one year), and two named parameters: [httpOnly: true] makes it invisible to the [JavaScript] on the page; [sameSite: 'lax'] prevents the browser from sending it with a POST request originating from another site;
    • lines 25–36: the original page is specified by the [Referer] header in the request (the misspelled version, with a single [r], is the one used in the HTTP standard), which the browser fills in with the URL from the page that contained the link. But this header comes from the client, which can put anything in it. Blindly redirecting to this address would turn our application into an *open redirect*: a malicious link bearing our domain name could send the user to a malicious site. Therefore, we retain only the path and parameters from URL (the [parse_url] function from [PHP] breaks it down into its components, storing them in an associative array), and we reject any path that begins with [//], which the browser would interpret as the address of another site. [Laravel] also provides [redirect()->back()] (or [back()]), which redirects to the previous page stored in the session (example 20), and not to the header [Referer]: we will use this in the case study.

// app/Http/Controllers/PagesController.php: Actions are not language-aware:
// they provide data, the views translate and format it

namespace App\Http\Controllers;

use App\Models\Produit;
use Brick\Math\BigDecimal;
use Carbon\CarbonImmutable;
use Illuminate\View\View;

class PagesController
{
    public function accueil(): View
    {
        return view('pages.accueil', ['nom' => 'Marie',
            'aujourdhui' => CarbonImmutable::create(2026, 9, 23)]);
    }

    public function produits(): View
    {
        return view('pages.produits', ['produits' => [
            new Produit('Clavier', BigDecimal::of('25')),
            new Produit('Souris', BigDecimal::of('12.5')),
            new Produit('Écran', BigDecimal::of('1149')),
        ]]);
    }
}

    Actions are language-agnostic: they provide raw data (a name, a date, amounts). Translation and formatting are handled by the views.
